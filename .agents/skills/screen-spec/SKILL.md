# Спецификации и демо-данные прототипа

Три шаблона, прочитай нужный инструментом `read` и заполняй по нему:

| Что описываешь | Файл | Шаблон |
|---|---|---|
| Страница `pages/<Имя>.html` | `pages/<Имя>.screen.md` рядом | `.agents/skills/screen-spec/references/template.md` |
| Виджет `widgets/<группа>/<Имя>/<Имя>.html` | `widgets/<группа>/<Имя>/<Имя>.md` рядом | `.agents/skills/screen-spec/references/widget-template.md` |
| Демо-данные | `data/<сущность>.js` | `.agents/skills/screen-spec/references/data-template.js` |

## Кто это читает

Двое, и спека пишется для обоих:

- **агент фронтенд-разработчика** — берёт наверстанный HTML, спеку и
  демо-данные и пишет ts/js реального продукта, а не прототип. Ему нужно:
  что это за сущность и где она у фронтенда, из чего собрана, какие у неё
  состояния и данные, какой файл прототипа какому файлу продукта соответствует;
- **человек**, который проверяет прототип: дизайнер, аналитик, владелец
  продукта. Поэтому спека — **по-русски**, как спеки до 24.09.2026 (решение
  владельца: английский знают не все).

Формат — общий знаменатель двух источников (решение владельца 24.09.2026):

- **дизайнерского дерева спек** (`ibp-design-spec`, по образцу фронтенда): у
  каждой страницы, фичи и виджета там один и тот же скелет — Purpose, Route,
  Layout, Components, States (Loading · Empty · Error · Disabled), Data
  dependencies (API · Redux · Permissions), Implementation mapping;
- **нашей спеки экрана** и **паспорта локального компонента ДС** — поведение,
  тексты, модальные окна, поля, права, переполнение, открытые вопросы.

Разделы спеки называются по-русски, а в скобках стоит английское имя
раздела из дизайнерского дерева: `## 8. Состояния (States)`. Так агент
разработки находит знакомые разделы, а человек читает свои. Английскими
остаются только идентификаторы: имена экранов и виджетов, ключи полей,
классы, пути.

Файл пишется **как данные, а не как проза**:

- таблицы вместо абзацев, одно утверждение — одна строка;
- имена компонентов ДС — как в `design-system/specs/_index.md`;
- явные классы и токены, а не описания «серый фон», «крупный заголовок».

## Правила заполнения

1. **Файл лежит рядом с HTML** и называется так же:
   `apps/postrade/deals-app/pages/Deal.html` → `Deal.screen.md`;
   `widgets/tiles/DealTeamTile/DealTeamTile.html` → `DealTeamTile.md`.

2. **YAML-шапка обязательна** — по ней спеку находят автоматически (сенсор,
   дерево README модуля).
   - Страница: `screen`, `kind`, `title`, `file`, `module`, `frontend`,
     `route`, `components` (компоненты ДС), `widgets` (что вшивает страница —
     `<группа>/<Имя>`, свои и соседей по разделу).
   - Виджет: `widget`, `type` (группа), `file`, `module`, `frontend` и поля
     паспорта локального компонента ДС (`name`, `purpose`, `ds`, `usedOn` …).
   - `kind` страницы — вид файла, по нему сенсор выбирает проверки: `screen`
     (по умолчанию) — экран в каркасе Layout; `document` — лист-документ,
     который пользователь получает файлом или видит в превью, без меню, крошек
     и PageHeader. Объявлять `document`, чтобы снять Б5 с экрана раздела,
     нельзя.

3. **`frontend` — пару ищешь сам.** Сначала README модуля, раздел «Имена
   фронтенда»; пока лежит полное дерево фронтенда
   `docs/misc/project-tree.md` — и в нём (модалки у фронтенда в основном в
   `features/`). Пара — сущность с тем же смыслом: русское название блока
   совпадает с английским у фронтенда («Связанные обеспечения» ↔
   `DealRelatedCollateralsTile`), подтверждают соседние сущности (тайл и его
   модалка: `DealPeriodTile` + `DealPeriodModal`). Пара нашлась — имя виджета
   или страницы такое же, `frontend:` — её путь. Пары нет или она другого
   вида (у фронтенда группа, а у нас тайл) — имя остаётся нашим с типом в
   конце, `frontend: new`, ближайшая сущность — строка в «Открытых вопросах».

4. **Раскладка — деревом**, как в дизайнерском дереве: блоки, их компоненты и
   виджеты, ширина в колонках. Каждый блок контента, кроме того, — строка
   таблицы: что за блок, каким компонентом или виджетом собран, сколько
   колонок из 12, что внутри.

5. **Состояния — минимум четыре подраздела** Loading · Empty · Error ·
   Disabled (у виджета — строки таблицы состояний паспорта). Состояния нет —
   так и написать, а не выбрасывать подраздел: пустой подраздел — вопрос, а
   не ответ.

6. **Данные — что нужно, а не как получить.** Поля — с теми же именами, что в
   typedef демо-данных (раздел ниже), с типом и смыслом; роли и флаги; файлы
   мока. Имена методов, хуков и стора API не придумываются — их выбирает
   разработка.

7. **Соответствие файлов — таблица «прототип → фронтенд (предложение)».**
   Путь продукта — по соглашениям его модуля (`src/pages/<Имя>/<Имя>Page.tsx`,
   `src/widgets/<группа>/<Имя>/<Имя>.tsx`; модалки у фронтенда — в
   `src/features/…`). Это предложение: окончательный путь выбирает разработка.

8. **Поведение описывается парой «триггер → результат»**, без ссылок на код.
   Пример: «Двойной клик по строке → открывается модальное окно
   «Редактирование заявки» (`.modal--w6`) с данными этой строки».

9. **Раздел «Открытые вопросы» не удаляется никогда.** Если вопросов нет —
   строка «Открытых вопросов нет». Всё, что было принято допущением, а не
   взято из ТЗ, попадает сюда явно, с пометкой «допущение».

10. **Не выдумывать предметную область.** Неясно, что означает поле, откуда
    берётся значение, какие бывают статусы, — строка в «Открытых вопросах»
    или `не решено (ДД.ММ.ГГГГ)`, а не придуманное описание. Придуманное
    неотличимо от факта и уедет в разработку как требование.

11. **Тексты интерфейса выписываются отдельно** — заголовки, подписи кнопок,
    плейсхолдеры, пустые состояния, тексты ошибок. Русский, без англицизмов,
    действия — инфинитивом («Добавить», «Выгрузить»).

12. **Свои разделы экрана** («Версии материала», «Скрипт экрана», «Дефекты
    ДС, найденные при сборке») — вставляются между стандартными, нумерация
    сквозная; стандартные разделы не выбрасываются.

13. **Спека описывает состояние, а не историю** (Б32): разделов «Правки
    ДД.ММ.ГГГГ» нет, история живёт в git.

Спеки, написанные до 24.09.2026, — в прежнем формате (без «Соответствия
файлов», пар во фронтенде, английских имён разделов). Они приводятся к
шаблону по задаче `docs/tasks/0003-specs-to-common-template.md`, а не
мимоходом при правке.

## Демо-данные — `data/*.js`

Образец — `references/data-template.js`. Разработчик превращает typedef в
TS-интерфейсы, поэтому данные прототипа устроены как ответ API:

1. **Обычный `<script>`**, не JSON (страницы открываются по `file://`):
   `window.MOCK_<СУЩНОСТЬ>` — массив записей, `window.<СУЩНОСТЬ>_LABELS` —
   подписи кодов; помощник выборки, если нужен, — отдельным файлом
   (`deals-store.js`).
2. **Каждый тип описан JSDoc** — `@typedef` с `@property` на каждое поле
   (тип и смысл по-русски), у массива — `@type`.
3. **Имена — английские, в стиле API фронтенда**: типы PascalCase с суффиксом
   `RsDto` / `RqDto` (`ClientUcpRsDto`, `RnpSearchRsDto`), поля camelCase,
   доменные сокращения как есть (`objectId`, `partyId`, `gosbName`,
   `terBankName`), перечисления — коды `UPPER_SNAKE` с отдельной картой
   подписей, суммы — числа, валюта — код ISO 4217 (`RUB`, Б26), даты —
   ISO-строки, форматируются при выводе.
4. **Источник имён — у каждого typedef**: `Source: DTO <Имя> (refs/dto/…)`,
   когда контракт бэкенда есть, или `Source: invented (ДД.ММ.ГГГГ)`, когда
   имена придуманы. DTO-файлы, которые даёт человек, кладутся в `refs/dto/`
   модуля или концепта; с их появлением придуманные имена заменяются на
   контрактные — в данных, спеках и разметке.
5. **Значения** — правдоподобные и детерминированные (без `Math.random`),
   русские там, где их показывает интерфейс. Их правят по ходу дизайна
   фичи — это нормально; имена и типы при этом держатся одними и теми же.

Файлы данных, заведённые до 24.09.2026, typedef ещё не имеют — задача
`docs/tasks/0004-typed-demo-data.md`.

## Что не пишется в спеке

- CSS и JS-код — он в HTML;
- рассуждения о том, почему выбран компонент;
- пересказ ТЗ своими словами без структуры;
- придуманные API-хуки, пропсы продукта и пути, выданные за решённые.

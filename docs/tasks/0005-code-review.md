## Находки

### R1 · P1 — параллельные сохранения теряют один из комментариев

**Место:** [.agents/proto-panel/store.js](../../.agents/proto-panel/store.js), строки 384–398, особенно 388–395.

```js
return readText(FILES.comments);
// ...
ops.forEach(function (op) { apply(model, op, added); });
var next = core.serializeComments(model);
return writeText(FILES.comments, next);
```

Чтение свежего файла и его замена не защищены от другой записи. Две вкладки могут прочитать одну версию, обе вычислить одинаковый следующий номер и затем по очереди заменить весь файл. Локальный флаг `saving` в интерфейсе не координирует вкладки; публичный API тоже допускает параллельные вызовы.

**Воспроизведение:** две независимые копии `store.js` подключены к одному поддельному `FileSystemDirectoryHandle`. Обе операции `add` удерживаются после получения одного снимка `comments.md`, затем продолжаются. Обе завершаются успешно, но первая запись исчезает:

```text
Результаты save: [[1], [1]]
comments.md: [{ n: 1, body: "From tab B" }]
Ошибки разбора: []
```

Это нарушает §9.3 ТЗ и критерий слияния без потерь. Такой же интервал существует между чтением в браузере и внешней правкой файла агентом.

**Исправление:** координировать весь цикл чтения, изменения и записи между вкладками одного приложения. Отдельно предусмотреть обнаружение внешнего изменения и явный конфликт: блокировка только внутри браузера не защищает от файлового редактора. Нельзя подтверждать сохранение двух операций, если в файле осталась одна.

**Проверка после исправления:** одновременные `add/add` и `add/status` из двух экземпляров хранилища сохраняют обе операции; внешняя правка между чтением и записью не затирается молча.

### R2 · P1 — незакрытый блок кода поглощает следующие комментарии

**Место:** [.agents/proto-panel/core.js](../../.agents/proto-panel/core.js), строки 657–675; сериализация тела — строки 693–699.

```js
if (FENCE_RX.test(l)) fence = !fence;
if (!fence && /^##(\s|$)/.test(l)) {
  finish(cur);
```

Флаг блока кода действует на весь файл. `cleanBody()` выпускает незакрытый блок без исправления или ошибки, а `parseComments()` после него перестаёт распознавать заголовки следующих записей. Разбор не сообщает об ошибке: следующие комментарии становятся частью текста предыдущего.

**Воспроизведение:** в модели два комментария; тело К-1 — строка «Пример», открывающая строка из трёх обратных кавычек с `js` и строка кода без закрывающего ограждения. К-2 содержит независимый текст. После `parseComments(serializeComments(model))`:

```text
Номера комментариев: [1]
Ошибки: []
Тело К-1 содержит "## К-2 · открыт": true
```

Сценарий доступен через обычную правку К-1 в панели, когда К-2 уже существует. К-2 исчезает как отдельная запись, его статус и контекст теряются для интерфейса и команд агента. Последующая правка тела или удаление К-1 может окончательно удалить и поглощённый текст.

**Исправление:** сериализация произвольного пользовательского текста должна сохранять границы записей. Например, нормализовать незакрытые ограждения внутри отдельного тела либо блокировать сохранение с понятной ошибкой. Перед записью проверять, что повторный разбор сохраняет набор номеров и содержимое записей. Для уже повреждённого файла нужна диагностируемая ошибка, а не успешный разбор усечённой модели.

**Проверка после исправления:** закрытые и незакрытые блоки кода, разные типы ограждений и заголовки внутри кода не меняют число соседних комментариев и их идентификаторы. Это пробел защиты формата: существующий ПН3 на данном примере молчит.

### R3 · P2 — ошибка записи зеркала приводит к дублированию при повторе

**Место:** [.agents/proto-panel/store.js](../../.agents/proto-panel/store.js), строки 395–398 и 276–280. Дополнительный путь — обработчик неудачного добавления в [.agents/proto-panel/tab-comments.js](../../.agents/proto-panel/tab-comments.js), строки 285–289.

```js
return writeText(FILES.comments, next).then(function () {
  return readText(FILES.flows);
}).then(function (flows) {
  return rebuildMirror(flows || '', next);
});
```

`comments.md` уже записан, когда начинается запись `panel-data.js`. Если зеркало записать не удалось, вся операция считается неуспешной. `flushDrafts()` оставляет исходный черновик, а обработчик нового комментария создаёт черновик. Повтор снова выполняет `add`, хотя комментарий уже существует на диске.

**Воспроизведение:** создать один черновик; разрешить запись `comments.md`, но заставить `createWritable()` зеркала вернуть ошибку; затем восстановить доступ и вызвать `flushDrafts()` повторно.

```text
После ошибки: comments.md = [К-1: "Retry me"], черновиков = 1
После повтора: comments.md = [К-1: "Retry me", К-2: "Retry me"]
```

**Исправление:** различать успешную запись основного файла и неудачное обновление производного зеркала. После фиксации комментария повторять восстановление зеркала, а не добавление. Сохранять идентичность операции/черновика до завершения восстановления; удалять из очереди только подтверждённые операции.

**Проверка после исправления:** сбои чтения `flows.yaml` и записи зеркала после записи комментария, затем повтор через «Повторить запись» и повторное подключение папки — ровно один комментарий.

### R4 · P2 — новое открытие по адресу шага может пропустить воспроизведение

**Место:** [.agents/proto-panel/runner.js](../../.agents/proto-panel/runner.js), строки 291–297; вызов при старте — `resume()` / `fromHash(true)`, строки 328–350.

```js
if (clean && onPage && cur >= k && cur < j) return run(flow, cur + 1, j, ...);
if (clean && onPage && cur === j) {
  // ...
  return Promise.resolve(true);
}
if (opts.fresh && onPage) return run(flow, k, j, ...);
```

Проверка `fresh` стоит после оптимизаций по старому состоянию сессии. В новом документе DOM сброшен, но сохранённый `pp.state` ещё может иметь `dirty: false`. Если открыть адрес того же шага после ухода из прототипа на внешнюю страницу в этой же вкладке, рантайм считает шаг уже достигнутым. Если целевой шаг позже сохранённого, выполняется только приращение без необходимых предыдущих действий.

**Воспроизведение:** в новой VM загрузить `runner.js` с адресом `A.html#pp=demo/ready` и сохранённым чистым состоянием `demo/ready`; вызвать `resume()`. Шаг `ready` содержит действие, однако результат:

```text
current: { flow: "demo", step: "ready", dirty: false, error: null, ... }
lastRun(): null
```

Хеш удалён, но действия шага не запускались. Нарушены §8.1 и §8.6 ТЗ: ссылка должна приводить к состоянию шага независимо от прежнего документа.

**Исправление:** обрабатывать новый документ до оптимизаций, использующих старое состояние, либо помечать прежнее состояние недействительным до `fromHash(true)`.

**Проверка после исправления:** новое открытие ссылки на тот же и на следующий шаг при сохранённом чистом состоянии выполняет весь путь от точки входа; обычный переход вперёд в живом документе сохраняет оптимизацию.

### R5 · P2 — при переполнении localStorage резервная запись недоступна для чтения

**Место:** [.agents/proto-panel/store.js](../../.agents/proto-panel/store.js), строки 57–72.

```js
var v = usable ? a.getItem(k) : (k in mem ? mem[k] : null);
// ...
} catch (e) { /* квота или запрет — держим в памяти */ }
if (s === null) delete mem[k]; else mem[k] = s;
```

`usable` вычисляется один раз при старте. Если хранилище первоначально доступно, но последующая запись отклонена, значение попадает в `mem`; чтение продолжает обращаться к прежнему `localStorage`. Черновик исчезает уже при следующем чтении, хотя `addDraft()` возвращает его идентификатор и интерфейс сообщает о сохранении.

**Воспроизведение:** поддельный `localStorage` успешно проходит стартовую пробу, затем его `setItem()` начинает выбрасывать `QuotaExceededError`. После `addDraft('Do not lose me')`:

```text
Идентификатор возвращён: true
store.drafts().length: 0
store.local.usable: true
```

**Исправление:** переключать чтение и запись на согласованное резервное состояние после отказа либо учитывать значения в памяти с приоритетом над диском, включая удаления. Сообщать пользователю, что данные живут только до перезагрузки; не показывать подтверждение устойчивого сохранения.

**Проверка после исправления:** хранилище доступно на старте и отказывает позднее — добавление, редактирование и удаление черновика работают в памяти, предупреждение о временном хранении видно.

### R6 · P2 — у недописанного комментария незаметно меняются страница и шаг

**Место:** [.agents/proto-panel/tab-comments.js](../../.agents/proto-panel/tab-comments.js), строки 37–52.

```js
if (f.custom) { out.page = f.page || null; out.step = f.step || null; }
else { out.page = pageNow(); out.step = autoStep(); }
// ...
if (next.custom) {
  next.page = 'page' in patch ? patch.page : cur.page;
  next.step = 'step' in patch ? patch.step : cur.step;
}
```

При обычном вводе сохраняются только `text` и `custom: false`. Контекст сохраняется лишь после ручной правки чипов или команды «Комментировать шаг». Если набрать замечание к странице A, закрыть шторку и перейти на B, восстановится тот же текст, уже привязанный к B и её текущему шагу.

**Воспроизведение:** исполнить обработчик `input` с текстом «Fix page A», затем восстановить форму при другом текущем адресе и шаге:

```text
До:      { text: "Fix page A", page: "A.html", step: "demo/a" }
Хранилище: { text: "Fix page A", custom: false }
После:   { text: "Fix page A", page: "B.html", step: "demo/b" }
```

Это противоречит §7.5: набранный текст и его контекст должны сохраняться при каждом вводе. Ошибка особенно существенна для дальнейшей работы агента по комментариям: замечание направляется к другому экрану.

**Исправление:** фиксировать текущие страницу и шаг при начале ввода и восстанавливать их вместе с текстом. Автоматический контекст пересчитывать для новой пустой формы; явное удаление чипов сохранять как выбор пользователя.

**Проверка после исправления:** ввод → закрытие → переход на другой шаг/страницу → открытие сохраняет исходный контекст, в том числе после перезагрузки.

### R7 · P1 — сохранение зависает навсегда: «нужно разрешение» + черновик

**Место:** [.agents/proto-panel/store.js](../../.agents/proto-panel/store.js): `ensureAccess()` (стр. 426) → `permit()` → `attach()` → `flushDrafts()` → вложенный `save()`; очередь страницы `pageQueue()` (стр. 434) и Web Locks `tabLock()` (стр. 444). Вход из интерфейса — `canWrite()` в [tab-comments.js](../../.agents/proto-panel/tab-comments.js) (стр. 126) пускает запись и в статусе `needs-permission`.

Вложенная запись встаёт в очередь за внешней, а внешняя ждёт вложенную — очередь ждёт сама себя; с Web Locks то же происходит на одной блокировке. Регресс правки R1: без очереди вложенная запись шла параллельно.

**Воспроизведение:** новая сессия браузера (статус «нужно разрешение»); «Добавить» → окно разрешения закрыли → комментарий стал черновиком; второе «Добавить» → «Разрешить».

```text
save за 1,5 с: не завершён; comments.md: []; черновиков: 1; статус: linked
следующая запись во вкладке: не завершена
```

В интерфейсе `saving` не снимается: «Добавить», «Сохранить» и статусы не работают до перезагрузки.

**Исправление:** разрешение спрашивать в жесте пользователя до очереди; изнутри записи папку подключать без записи черновиков, черновики писать после выхода из очереди.

**Проверка после исправления:** `needs-permission` + черновик + запись — завершается, на диске оба комментария, черновиков нет.

### R8 · P1 — контроль повторного разбора сравнивает сырой текст с нормализованным

**Место:** [.agents/proto-panel/store.js](../../.agents/proto-panel/store.js), `roundTrip()` (стр. 412–424): тело из модели (сырой текст, `apply()` стр. 391 и 398) сравнивается с телом после `cleanBody()` ([core.js](../../.agents/proto-panel/core.js), стр. 698) и `trimBlock()` разбора. Регресс правки R2.

**Воспроизведение:**

```text
add «## Раздел\nтекст»              → «Запись изменила бы состав комментариев — сохранение остановлено»
add «# Раздел\nтекст»               → то же
add «Пример\n```js\nconst x = 1;»   → то же — ровно тот случай, который R2 чинил закрытием блока
comments.edit(n, «текст\n»)         → то же
файл с «# …» в теле К-1 (ПН3 молчит, гейт зелёный) → любая запись панели, включая смену статуса, отклонена
```

Каскад: неудачное добавление становится черновиком, `flushDrafts()` пишет все черновики одним пакетом, и при каждой загрузке `init()` → `attach()` → `flushDrafts()` падает, а `catch` ставит статус `mirror` (стр. 325) при выданном разрешении. Две загрузки подряд: статус `mirror`, оба черновика на месте, `comments.md` пуст — запись в приложении выключена. Противоречит README панели (раздел «comments.md»: заголовки понижаются до `###`) и §6.2 ТЗ.

**Исправление:** сравнивать с канонической записью — тело через `cleanBody()`, метаданные — одной строкой; сбой записи черновиков не отключает папку.

**Проверка после исправления:** через `store.save`, а не только ядро: заголовки, незакрытый блок, чужой комментарий с `# …`, `edit` с переводом строки; старт с таким черновиком — папка подключена, черновик записан.

### R9 · P2 — R3 закрыт не до конца: сбой после записи всё ещё даёт дубль

**Место:** [.agents/proto-panel/store.js](../../.agents/proto-panel/store.js), `attemptOnce()` (стр. 483–486): контрольное чтение `comments.md` и чтение `flows.yaml` идут уже после записи, их ошибка отклоняет `save`. [tab-comments.js](../../.agents/proto-panel/tab-comments.js) (стр. 297) на любую ошибку создаёт черновик с новой отметкой времени, а повтор идёт без подписей (`usePre = false`, стр. 514).

**Воспроизведение:**

```text
flows.yaml занят (NotReadableError) после записи → save отклонён; comments.md: [К-1 «Один раз»]
«Повторить запись» → [К-1 «Один раз», К-2 «Один раз»]
то же при сбое контрольного чтения comments.md
```

Кейс селфтеста 18е проходит впустую: после 18д черновиков не остаётся, повтору нечего писать.

**Исправление:** после сверки «на диске то, что писали» операция состоялась: сбой чтения `flows.yaml` — это сбой зеркала (предупреждение, данные в памяти), сохранение успешно. Неподтверждённая запись повторяется с подписями; черновик после сбоя получает время и автора исходной операции; черновики пишутся с подписями всегда.

**Проверка после исправления:** сбой чтения `flows.yaml` и контрольного чтения после записи, затем повтор через интерфейс — ровно один комментарий.

### R10 · P2 — R5: хранилище, закрытое со старта, не даёт предупреждения

**Место:** [.agents/proto-panel/store.js](../../.agents/proto-panel/store.js): `volatile()` (стр. 61) учитывает только отказ на ходу; при `usable === false` `set()` пишет в память и флаг не ставит (стр. 73); `draftsVolatile()` (стр. 124). Флаг к тому же общий и не сбрасывается.

**Воспроизведение:**

```text

  → Alert «Комментарии сохраняются только в этом браузере», после перезагрузки черновиков нет
отказ записи другого ключа (pp.ui пишется на каждый ввод): черновик в localStorage, draftsVolatile=true
```

Нарушает §8.2 ТЗ: без хранилища панель предупреждает, что черновики не переживут перезагрузку.

**Исправление:** признак временного хранения — по ключу: хранилище закрыто или этот ключ живёт в памяти.

### R11 · P3 — R6: снятие одного чипа снимает оба; стёртый текст держит прежнюю страницу

### R13 · P3 — черновики общие для вкладок, их запись — нет

**Место:** [.agents/proto-panel/store.js](../../.agents/proto-panel/store.js), `flushDrafts()` (стр. 300–305): список берётся до очереди и блокировки, после записи удаляются все черновики.

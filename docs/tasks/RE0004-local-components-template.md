# Локальные компоненты: единый шаблон

## Коротко

- **Что не так.** Правила локальных компонентов (виджетов: тайлов, таблиц, окон,
  поповеров) записаны в пяти местах и разошлись. Паспорта написаны по трём разным
  шаблонам, поэтому вкладка «Документация» у каждой страницы витрины своя: разные
  разделы, разный порядок. Вкладка «Конструктор» тоже: одни и те же оси названы
  по-разному, состояния данных спрятаны в свои переключатели.
- **Зачем.** Человек и агент открывают любой компонент и находят нужное на одном и
  том же месте — как на страницах компонентов ДС. Другая команда заводит свои
  локальные компоненты по тому же шаблону.
- **Решение.** Один канон разделов паспорта и страницы — в шаблоне ДС
  `templates/local-component/Component.md`; правила — на странице ДС «Локальные
  компоненты» 2.000; генератор витрины собирает вкладку «Документация» по канону и
  не пропускает паспорт с разделом мимо канона (КТ2). Уникальное у компонента не
  теряется — оно живёт h3 внутри канонических разделов.
- **Объём.** Страница правил и шаблон ДС; 32 паспорта и 15 сценариев демо;
  генератор `kit-build.mjs` и рантайм витрины `kit-docpage.js`; указатели харнеса.

Решения человека 02.10.2026:

| Вопрос | Решение |
|---|---|
| Канон разделов | «по схеме виджета» — 14 разделов (раздел 2) |
| Как другие команды получают витрину | ДС (правила и шаблон) + харнес (генератор `kit-build.mjs` и оболочка витрины). Ручная витрина `Component.doc.html` из шаблона ДС убирается: второй путь к той же странице разъехался бы с генератором |
| Паспорта | все сейчас, по этапам; `rulesVersion` → 2.000. В вопросе стояло «30» — паспортов 32 |
| Как держать канон | расширение существующего кода КТ2 в шаге `kit`; новых сторожей и шагов гейта нет |

## Objective

У всех локальных компонентов — один шаблон папки, одна шапка паспорта, один набор
и порядок разделов вкладки «Документация» и одна конвенция вкладки «Конструктор».
Правило записано один раз — в ДС; харнес, витрина и README ссылаются на него.
Содержание паспортов при переезде не теряется — это доказано сравнением, а не
просмотром.

## 2. Канон вкладки «Документация»

Источник канона — заголовки `##` шаблона ДС `templates/local-component/Component.md`:
генератор читает их оттуда, копии списка в коде нет. Таблица на странице правил ДС —
пояснение к тем же заголовкам. В паспорте h2 пишется с английским именем в скобках (для
агента разработки, скилл `screen-spec`), на странице показывается русская часть;
сопоставление — по русской части.

| № | h2 в паспорте | Генератор добавляет | Свои темы h3 — примеры из нынешних паспортов |
|---|---|---|---|
| — | шапка паспорта | шапку страницы: имя, назначение, тип, категория, версия, дата | — |
| 0 | — | **Паспорт** — карточка: тип, модуль, папка, пара во фронтенде, где стоит, страницы, открывает / открывается из / как открывается / зависит от, варианты, владелец, дизайнер, требования, версия, версия правил. Сливает нынешние «Паспорт коротко» и «Связи» | — |
| 1 | Описание (Purpose) | — | «На странице сделки — «КНР»» |
| 2 | Раскладка (Layout) | — | сетка окна (из «Состава» `DealTeamModal`) |
| 3 | Компоненты (Components) | «Из чего собран»: компоненты ДС со ссылками, локальные компоненты, подчасти, файлы | — |
| 4 | Поля (Fields) | — | «Типы узлов», «Признаки», «Доступность полей по типу недвижимости» |
| 5 | Права (Permissions) | — | — |
| 6 | Состояния (States) | «Все состояния рядом» в конце раздела | «Свои состояния», «Варианты состава» (бывшая «Витрина») |
| 7 | Обязательность заполнения (Required) | — | — |
| 8 | Переполнение (Overflow) | — | — |
| 9 | Поведение (Behavior) | — | «Связанные артефакты» (таблица триггеров), «Правила состава и проверки», «Поведение выбора», «Проверка и сохранение», «Когда тайл показывается», «Связи с другими модулями», «Вложенное окно подтверждения» |
| 10 | Данные (Data dependencies) | — | «API — что нужно от бэкенда», «Mock — демо-данные прототипа» |
| 11 | Для разработчиков (Implementation) | — | «Параметры метки (Props)», «Скрипт окна» / «Скрипт тайла», «Соответствие файлов (Implementation mapping)» |
| 12 | Осознанные отклонения (Deviations) | — | отклонений нет — строка «Отклонений нет» |
| 13 | Открытые вопросы (Open questions) | — | раздел не удаляется никогда; вопросов нет — «Открытых вопросов нет» |

Правила канона:

- порядок фиксирован, новых h2 нет — своё становится h3 внутри канонического раздела;
- неприменимый раздел остаётся с одной строкой «Не применимо: …», неизвестное —
  `не решено (ДД.ММ.ГГГГ)`, а не догадка;
- h3 внутри переезжающего раздела становятся h4 (генератор показывает до h4);
- строка «Правка временно запрещена (Disabled)» уходит из обязательного набора — так
  решено в ДС 1.005; английский якорь `Disabled` переезжает на «Только просмотр»
  (скилл `screen-spec`, п. 5: у разработки есть раздел Disabled). Выключенный элемент
  внутри компонента — строка списка, кнопка, карточка — это строка «Своих состояний».

## 3. Канон вкладки «Конструктор»

Порядок контролов задаёт рантайм витрины по ключу контрола, подписи стандартные:

| Ключ | Подпись | Откуда |
|---|---|---|
| `state` | Состояние данных | селекторы `[data-state]` в CSS виджета + `states` сценария |
| `mode` | Режим прав | селекторы `[data-mode]` в CSS виджета |
| `variant` | Вариант — или имя оси предметной области («Тип ФИ») | закрытый список `variants` паспорта; сценарий |
| `example` | Пример данных | `fixtures.json`, когда образцов несколько |
| `long` | Длинные значения | ключ `long` в `fixtures.json` |
| свои | словами предметной области («Есть Private Equity») | сценарий |
| `width` | Ширина, px | метка страницы-хозяина; у тайла, таблицы, подчасти |

- Состояние данных — только осью `state`: никаких «Вид: Пусто / Ошибка».
- Подписи своих состояний и режимов — полем `labels` сценария, не в общем рантайме.
- Вид контролов — конвенция docs-split ДС: да/нет — свитч, 2–3 варианта —
  ButtonGroup, 4 и больше — список; подписи вариантов самодостаточные.
- Вкладка «Код» не меняется: `.html`, `.css`, `.js` виджета как есть.

## 4. Шапка паспорта

Порядок полей — как в шаблоне. Поля `widget`, `file`, `module` не пишутся: их даёт путь
папки, генератор показывает их в «Паспорте». `type` — кодом.

| Поле | Обязательно | Что |
|---|---|---|
| `name` | да | название словами продукта |
| `type` | нет — по группе папки | `tile` · `table` · `modal` · `popover` · `context-menu` · `part` (подчасть) |
| `category` | да | одна категория из списка проекта (`project.json → localKit.categories`) |
| `purpose` | да | одна строка: зачем компонент на экране |
| `version`, `updated` | да | М.ммм и ДД.ММ.ГГГГ |
| `rulesVersion` | да | версия правил ДС, по которой заполнен паспорт; после этой задачи — 2.000 |
| `owner`, `designer` | да | неизвестное — `не решено (ДД.ММ.ГГГГ)` |
| `frontend` | да | пара во фронтенде или `new` |
| `ds` | да | компоненты ДС, из которых собран |
| `uses` | если есть | локальные компоненты внутри |
| `usedOn` | да | экраны и место на них |
| `opens` | если есть | что открывает: окна, поповеры — именем виджета или путём до паспорта |
| `artifactOf` | у окна, поповера | чей он артефакт |
| `opensFrom` | у окна, поповера | триггер фразой |
| `dependsOn` | если есть | от кого зависит и как |
| `variants`, `modifiers` | если есть | закрытые списки |
| `requirements`, `knowledge` | если есть | требования и исследования |

Связь «открывает» записывается с обеих сторон: `opens` у открывающего, `artifactOf` у
окна — как в правилах ДС и как уже сделано в большинстве паспортов. Генератор показывает
связь и тогда, когда записан один конец, но правило — оба.

### Э1 · Правила и шаблон в ДС
1. `design-system/patterns/LocalComponents/LocalComponents.html` → 2.000: рамка («форма

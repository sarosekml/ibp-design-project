# Сенсор экрана видит CSS тайлов в отдельных файлах

## Коротко

- **Что не так.** Модульная страница держит стили каждого тайла и модалки в
  своём файле (`widgets/<группа>/<Имя>/<Имя>.css`), ассемблер подключает их в
  собранную страницу `<link rel="stylesheet">` (метка `<!-- @lc-css -->`).
  Браузер применяет эти файлы наравне с `<style>`, а сенсор раскладки
  (`.agents/tools/layout-check.mjs`) читает только стили ДС и встроенный
  `<style>` страницы. Файлы тайлов для него не существуют.
- **Что из этого выходит сейчас.** На `apps/postrade/deals-app/pages/Deal.preview.html`
  правило Б4 объявляет «выдуманными» 66 классов (`lc-knr`, `lc-deal-terms`,
  `lc-deal-team`… — все тайлы и модалки), хотя каждый объявлен в CSS своего
  тайла и страница в браузере оформлена полностью. Колонки сетки полей тайла
  (`grid-template-columns` в классе сетки) сенсор не читает — пишет «нет
  repeat(N) в .tile__grid — колонки не читаются» и считает геометрию по
  догадке. Из-за Б4 статистика уроков показывает регресс Л69, полный гейт —
  красный.
- **Почему срочно.** Скоро все страницы будут собираться так: тайлы всегда в
  отдельных файлах. Без правки ложный Б4 и слепая геометрия будут на каждой.
- **Решение.** Сенсор читает стили экрана так же, как браузер: встроенный
  `<style>` плюс локальные файлы, подключённые `<link rel="stylesheet">`.

## Objective

Сенсор оценивает модульную страницу по тем же стилям, которые применяет
браузер: классы из CSS тайлов — существующие, колонки сетки тайла читаются из
его CSS. Класс, объявленный в файле, который страница не подключила, остаётся
дефектом Б4.

## 1. Как сейчас (замер 26.09.2026)

- `checkMechanics` строит вход `styleSrc` — только встроенные `<style>`
  страницы. Его читают три правила: **Б4** (известные классы), **K12**
  (правило `@container`, перебитое инлайн-стилем) и **З10** (у экрана с
  несколькими рядами тайлов есть `@container screen`).
- Колонки сетки полей тайла (`analyzeTile`, вход геометрии K1, K5, K6, K9) —
  только из инлайн-`style="grid-template-columns: repeat(N…)"` на
  `.tile__grid`. Правило в классе сетки не читается ни во встроенном
  `<style>`, ни в файле тайла.
- Сенсор проверяет собранный файл (`*.preview.html`); исходник с
  `<ds-include>` и фрагменты пропускает — `<link>` на CSS тайлов есть именно в
  собранном файле.
- Линтер ДС `<link>` уже читает (правило A2: классы компонента есть, а
  `<link>` на его CSS нет) — сенсор разошёлся с ним.

## 2. Решение

Всё — в `.agents/tools/layout-check.mjs`:

1. **Стили экрана — одна функция** `screenStyles(html, pagePath)`:
   `{ own, linked, all }`. `own` — встроенные `<style>`, как сейчас.
   `linked` — файлы из `<link rel="stylesheet" href="…">` вне HTML-комментариев:
   `href` относительный (без схемы, без `//` и `/` в начале), файл внутри
   проекта, не в `design-system/` (стили ДС подключает загрузчик, поштучные —
   дефект Б1) и существует. `all` — `own` и `linked` вместе. Считается один раз
   в `checkOne` и передаётся правилам.
2. **Б4** — известные классы из стилей ДС и `all`. Класс из файла, который
   страница не подключила, по-прежнему дефект. Тексты находки и прохода
   называют и файлы экрана.
3. **K12** — правила `@container` из `all`: в файле тайла тот же дефект
   (адаптивное правило, перебитое инлайн-стилем в разметке тайла).
4. **З10 — без изменений**, только `own`: правило про перестроение РЯДОВ
   тайлов на странице; `@container` в файле тайла перестраивает поля внутри
   тайла и страничное правило не заменяет.
5. **Колонки сетки полей** — если инлайн-стиля нет, из правил `all` верхнего
   уровня (вне `@media` / `@container` — геометрия считается для широкой
   раскладки) с `grid-template-columns: repeat(N …)`: последний простой
   селектор — классы самой сетки, остальные классы селектора — классы тайла;
   атрибуты и псевдоклассы не учитываются; при нескольких подходящих правилах
   берётся последнее (каскад при равной специфичности).

**Вне задачи:** K4 на `Deal.preview.html` — «Сроки сделки» и «КНР» по 3
колонки из 12 при 3 полях, правило «ширина по объёму» требует от 4. Это
отступление раскладки от правила композиции, а не ошибка и не слепота сенсора:
тайлы бывают разные, отступление не трогается (решение 26.09.2026).

## 3. Проверка

**Пары фикстур сенсора** (`.agents/tools/fixtures/`, доказательство —
`lessons-cli verify --corpus sensor`):

- `_linked.ok.html` + `_linked/fx-lnk.css` — эталон варианта: тайл, чьи классы
  и сетка полей (`repeat(3)` на тайле 6/12) объявлены только в подключённом
  файле. Молчат Б4 и K5.
- `Б4@linked.bad.html` — тот же экран без `<link>` на файл тайла (файл лежит
  рядом, но не подключён): Б4 обязан сработать.
- `K5@linked.bad.html` — тот же экран, у сетки ещё класс
  `fx-lnk__grid--dense` (`repeat(4)` в том же файле): ячейка уже 240 px, K5
  обязан сработать — значит колонки читаются из файла тайла.

**Откат:** на сенсоре до правки `verify` не доказывает все три фикстуры (Б4
срабатывает на эталоне варианта, K5 не видит колонок).

**На рабочих страницах:** `gate --full` — на `Deal.preview.html` нет Б4,
предупреждение «колонки не читаются» сменяется оценкой K5 по настоящим
колонкам; остаётся K4 (вне задачи). Остальные экраны — без новых FAIL.

## Риски

| Риск | Что делаем |
|---|---|
| Новые находки K5/K1/K6 на экранах, где колонки раньше не читались | это точная оценка вместо догадки; FAIL разбираются по одному, предупреждения — в отчёт |
| `<link>` на чужой или удалённый CSS засчитает классы, которых нет у экрана | берутся только локальные файлы внутри проекта и вне ДС; файла нет — не засчитывается |
| Правило сетки под `[data-state]` или в `@container` даст неверные колонки | верхний уровень CSS и классы без атрибутов — оценка широкой раскладки, как у всей геометрии сенсора |

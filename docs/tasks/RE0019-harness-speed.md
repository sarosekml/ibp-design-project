# Ускорение харнеса

## Коротко

- **Продолжение RE0018.** Там починен гейт на рабочем устройстве, заведены короткие спеки
  концептов и параллельная сборка виджетов. Здесь — следующие шесть направлений, которые
  человек выбрал 14.10.2026.
- **Рамки — те же:** модель — данность, от её владельца ничего не требуем; проверки ДС и
  приёмка не ослабляются; правки ничего не ломают в проекте.
- **Порядок:** каждый этап реализуется отдельно, в своей сессии, со своей проверкой и
  **только по явному разрешению человека**.
- **Ожидание (оценка, не замер):** полный гейт на рабочем устройстве 25–40 → ~4–6 мин; обычный
  гейт концепта ~1–2 мин → ~15–30 с; вход сборщика на каждом ходу −~30 тыс. токенов; вывод на
  задачу масштаба RE0017 −15–20 тыс. токенов.

## Objective

Сократить время проверок и объём того, что модель читает и пишет на каждом ходе, не меняя
состав проверок и не трогая модель.

## Решения человека (14.10.2026)

| Вопрос | Решение |
|---|---|
| Как убрать повтор глобальных правил в линтере экрана | флаг в обёртке линтера ДС `design-system/tools/ds-lint-cli.mjs`; сам линтер не трогается — явное поручение на правку ДС в этом объёме |
| Как держать короткий чек-лист сборщика в согласии с полными | генерат + сверка в гейте — новая сверка согласована |
| Насколько глубоко сокращать инструктаж | вынести, не удалять: история — в журнал уроков, сценарий страниц документации — в его скилл, повторы — одному владельцу; правило `process.md` §13 переписывается |
| Убрать `CHANGELOG.md` у виджетов концепта | **отклонено** |

## Э1. Линтер на экране — без повтора глобальных правил ДС

**Замер (13–14.10.2026, машина автора):** запуск линтера на один экран — 4,2 с, из них 3,4 с —
глобальные правила всей ДС (`globalChecks` в `ds-lint.js`), которые прогоняются при каждом
вызове. Проверка самого экрана — 0,2–0,3 с. Глобальные правила читают только ДС; для правок ДС у
гейта есть отдельный шаг `lint-global`. Пакетный запуск не годится: при >3 файлах линтер пишет в
журнал одну строку «N файлов», и `stats` теряет привязку дефектов к экранам.

**Правка:**
- `design-system/tools/ds-lint-cli.mjs`: флаг `--no-global` → `run(targets, { global: false, … })`;
  шапка файла и `design-system/tools/ds-lint.md` — строка о флаге; запись в журнал не меняется.
  Запись в журнале изменений ДС — если её требуют правила ДС для правки `tools/`.
- `.agents/tools/lessons-cli.mjs`, `gateStep`, шаг `lint`: для целей вне ДС (экраны `apps/`) —
  `--no-global`. Страницы ДС и пакет `lint-pages` — без изменений.
- **Обязательно вместе с флагом — `stats`** (`lessons-cli.mjs`): «живой / исчез» считается по
  последним 10 прогонам инструмента. Глобальные коды (например, D4) сейчас стоят в каждой
  строке экрана; после флага они останутся только в прогонах `lint-global`, и `stats` ложно
  покажет их «ИСЧЕЗ» (= «обучение»). Для кодов из `lintRepoIds()` свежесть считать по прогонам,
  где глобальные правила выполнялись (цель — не экран приложения).

**Не ломается (проверено по коду):** `verify --corpus lint`, `ds-check --all` и пакет страниц ДС
зовут обёртку без флага; регресс (`findRegressions`) пофайловый — пропажа глобальных кодов на
экранах регрессом не считается; правка обёртки сама поднимет в гейте `verify-lint`, `anchors`,
`lint-global`, `parity`.

**Эффект:** экран 4,2 → ~0,3 с (на рабочем устройстве ~7,5 → ~0,5 с); полный гейт — линтер 82
файлов 289 → ~30 с (на устройстве ~10 → ~1 мин); обычный гейт концепта −20–60 с.
Уверенность высокая — замер.

**Проверка:** отчёт по 3–4 экранам с флагом и без — строки страницы совпадают, пропадают только
глобальные; `verify --corpus lint`; `stats` до и после — те же состояния глобальных кодов; гейт.

**Сделано (14.10.2026):** флаг `--no-global` в `ds-lint-cli.mjs` (шапка, `tools/ds-lint.md`, строка в
`CHANGELOG.md` ДС); шаг `lint` гейта для цели вне ДС зовёт линтер с флагом; в `stats` свежесть
кодов из `lintRepoIds()` — по последним 10 прогонам, цель которых не экран (`isScreenTarget`:
каталог трека или хаб). Замер на машине автора: 4 экрана — 3,6–4,0 → 0,65–0,7 с, строки
страницы совпадают, пропадает только глобальный D4; шаг `lint` в гейте — 0,5 с. `stats` до и
после — те же состояния (живые D4 P5, исчезли D7 D9 P4). Гейт `ВЕРДИКТ: OK` (13 шагов, в том
числе `verify --corpus lint`, `anchors`, `lint-global`, `parity`), `gate --changed` по экрану —
OK, `vendor-scan` — OK.

## Э2. Пофайловые шаги гейта — параллельно

Сенсор ~0,7 с на экран (на устройстве ~1,1 с), линтер после Э1 ~0,3 с; шаги идут строго по
одному (`execFileSync` в цикле `gate()`). Пакетирование ломает пофайловый учёт (долг, прогресс
прерванного прогона, проверка «прогон записан в журнал»), поэтому — пул параллельных процессов.

**Правка (`lessons-cli.mjs`, только харнес):**
- шаги `sensor`, `lint`, `split`, `syntax` — асинхронный `spawn` пулом из `min(4, число ядер)`;
  репозиторные шаги — по одному, как сейчас;
- `gate()` асинхронный: `process.exit(gate())` → `gate().then((c) => process.exit(c))`;
- файл прогона (`RUNLOG_FILE`) гейт создаёт до запуска пула — чтобы параллельные процессы не
  запускали вращение журнала одновременно;
- **обязательно:** проверка «прогон записан в журнал» (`MUST_LOG`) сейчас считает строки до и
  после шага — при параллельности она даст ложные FAIL; заменить на «в журнале есть строка с
  этой целью» (`readRuns` из `runlog.mjs`);
- прогресс прерванного прогона — по завершении каждого шага, как сейчас; порядок вывода — как сейчас.

**Не ломается:** одновременная дозапись коротких строк в журнал безопасна; вращение журнала
удаляет с `force` и гонку переживает; вывод каждого процесса собирается отдельно.

**Эффект:** пофайловая часть быстрее в 3–4 раза; полный гейт здесь ~6,5 → ~2–3 мин, на
устройстве вместе с Э1 ~25–40 → ~4–6 мин. Уверенность средняя — зависит от ядер и диска.

**Проверка:** полный прогон до и после — то же число шагов и вердикты, строк в журнале не меньше
числа пофайловых шагов; шаг без записи в журнал по-прежнему даёт FAIL `ЖУРНАЛ:`.

**Сделано (14.10.2026):** `gate()` асинхронный; подряд идущие шаги `sensor`, `lint`, `split`,
`syntax` — пулом `runGateStepAsync` (`spawn`) из `GATE_JOBS = min(4, ядер)`, репозиторные — по
одному; результаты — по индексу, вывод в прежнем порядке; прогресс — по завершении каждого шага.
Файл прогона гейт создаёт до пула и вращает журнал сам; пустой в конце удаляется. Проверка
`MUST_LOG` — по строке с целью шага (`step.log`, `readRunFile` — новый экспорт `runlog.mjs`).
Замер на машине автора (36 ядер, пул 4): полный гейт 509 → 331 с, 817 шагов и `ВЕРДИКТ: OK` в
обоих, состав шагов совпадает, строк в файле прогона 240 и 240. Шаг без записи в журнал (запись в
обёртке линтера временно отключена) — FAIL `ЖУРНАЛ:` при том, что параллельный сенсор свои строки
записал. В строке «сенсор — файлов: N (… с)» время теперь — сумма по шагам, а не время по часам.
Остаток полного гейта — репозиторные `verify --corpus lint` (~140 с) и `verify --corpus sensor`
(~35 с): в Э2 не входили.

## Э3. Короткий чек-лист самопроверки сборщика

Сборщик на самопроверке грузит `screen-review` (53 тыс. символов) и `composition-review`
(25 тыс.), и они уходят модели на каждом следующем ходе. По `lessons-cli coverage` из 81 пункта
59 закрыты сенсором и линтером (сборщик их и так запускает); вручную — 21 «суждение» и 6
закрытых частично. Самопроверка остаётся — меняется только то, что сборщик читает.

**Правка:**
- `lessons-cli brief [--check]` — подкоманда рядом с `coverage`, переиспользует её разбор
  таблиц (`checklistIds`) и `coverage.json`. Генерат
  `.agents/skills/screen-review/references/self-check.md`: пункты «суждение» и «частично»
  дословно из таблиц, у частичных — что не закрыто; в шапке — «остальные N пунктов закрывают
  сенсор и линтер — запусти их», «СГЕНЕРИРОВАН — руками не править».
- Гейт: правка любого из двух `SKILL.md`, `coverage.json` или `layout-check.mjs` → шаг
  `brief --check`.
- `screen-builder.md`, шаг 6: пп. 2–3 → «пройди `self-check.md` по пунктам». Приёмщик не
  меняется — оба полных чек-листа.
- `stages.json`, этап `build`: в «читает» — `self-check.md` (сейчас самопроверка в смете не
  учтена вовсе); `ctx-budget --selftest`.

**Не ломается:** `coverage`, `anchors`, `check` читают пункты только из двух исходных
`SKILL.md` — генерат их не задвоит; генерат подхватит `docs-index`.

**Эффект:** −78 тыс. символов → +~10–12 тыс. на входе сборщика, примерно −30 тыс. токенов на
каждом ходе после самопроверки. В минутах — только после замера на устройстве.

**Сделано (14.10.2026):** `lessons-cli brief [--check]` → генерат
`.agents/skills/screen-review/references/self-check.md`: 28 пунктов из 81 — «суждение» (21),
«частично» (6, с тем, что не закрыто) и З13 («посильно, не написано»: сторожа нет, без него пункт
не проверял бы никто). Строки таблиц — дословно, по разделам источника, с шапкой таблицы. Шаг гейта
`brief` — при правке двух `SKILL.md`, `coverage.json`, `layout-check.mjs`, самого генерата и
`lessons-cli.mjs`; в полном гейте — тоже. `screen-builder.md` шаг 6 и `screen-assembly` п. 8 —
«сенсор + `self-check.md`»; приёмщик не менялся. `stages.json`, этап `build` — `self-check.md` в
«читает»; карта документации пересобрана (`docs-index.mjs`).
Объём: 79 тыс. → 21 тыс. символов; по смете `ctx-budget` 18,8 тыс. → 4,9 тыс. токенов, то есть
−~14 тыс. на каждом ходе после самопроверки (оценка плана −30 тыс. была завышена: строки
композиции длинные, с колонкой «Как выявить»). Проверки: `brief --check` ловит ручную правку
генерата (FAIL), `coverage`, `anchors`, `check`, `ctx-budget --selftest` — OK; гейт и `vendor-scan` — OK.

## Э4. Генератор заготовок `scaffold.mjs`

На виджет агент пишет 6 файлов, хотя шаблон есть в ДС (`design-system/templates/local-component/`);
страница — копия `templates/screen/Screen.html` (~2,5 тыс. токенов, которые агент переписывает
выводом). Шапки YAML, заголовки разделов, CHANGELOG — шаблонный вывод.

**Правка:** `.agents/tools/scaffold.mjs` (`--dry`, `--selftest`, корень из `project.mjs`):
- `widget <приложение> <группа> <Имя> --category <категория>` — файлы из шаблона ДС;
  `category` сверяется со списком раздела (`project.json → localKit`), иначе генератор
  витрины даст КТ2; `purpose: не решено (дата)`; в концепте — короткий паспорт (все «##»
  шаблона, под каждым «—»); `<Имя>.js` — каркас с шапкой API;
- `page <приложение> <Имя>` — копия `Screen.html` с заменой, описанной в
  `screen-assembly/SKILL.md` §2 п. 1 (подключение ДС → `ds-config.js` и `ds-body.js`,
  строка пользователя меню → хаб); пути — относительные от страницы до
  `project.json → boot.head`, `boot.body` и страницы хаба; спека — `concept-template.md` в
  `drafts/`, заголовки `template.md` в модуле, шапка заполнена;
- существующий файл не перезаписывается никогда;
- после себя печатает, что запустить дальше (`assemble.mjs`, `kit-build.mjs`,
  `module-readme.mjs`): до этого гейт законно красный — промежуточное состояние;
- правила: `screen-assembly` шаг 1 (каркас — командой), `screen-spec` (заготовку создаёт
  `scaffold`), `ai-designer.md` «Собери экран» (заготовки — до раздачи параллельных заданий);
  гейт — `scaffold --selftest` при правке файла.

**Эффект:** масштаб RE0017 — −15–20 тыс. токенов вывода (~4–8 мин при 40–80 ток/с) и меньше
ходов. Уверенность средняя.

**Проверка:** во временной копии — заготовка страницы и виджета концепта → `layout-check` без
Б1/Б34, `kit-build --check`, `assemble --check`, гейт; повторный вызов на тот же путь — отказ.

**Сделано (14.10.2026):** `.agents/tools/scaffold.mjs` — `widget` и `page`, `--dry`, `--selftest`
(11 кейсов на настоящих шаблонах ДС и спек), коды ЗГ1–ЗГ4; при любом ЗГ ничего не пишется.
Сверх плана: `--name`, `--purpose` (виджет), `--title` (страница), `--no-js`; неизвестное в
шапках — `не решено (дата)`; категория — тем же разбором, что у витрины (`kitConfig`).
Шапка-комментарий шаблона (о самом шаблоне) не переносится ни в страницу, ни во фрагмент виджета.
Гейт: шаг `scaffold-selftest` — при правке `scaffold.mjs`, `kit-build.mjs`, `project.mjs`,
шаблонов ДС `templates/local-component/*` и `templates/screen/*`, шаблонов спек
`concept-template.md` и `template.md`; в полном гейте — тоже. Правила: `screen-assembly` §2 п. 1
(каркас — командой), `screen-spec` (заготовку спеки создаёт команда), `screen-builder.md`
(папка виджета — командой), `ai-designer.md` «Собери экран» п. 4 (заготовки — до раздачи
параллельных заданий), `process.md` §5 — указатель; строки в `.agents/README.md` и в памятке
витрины `apps/local-components/README.md`.
Проверка во временной копии репозитория: концепт с заготовкой страницы и виджета, виджет вшит
меткой → сенсор по `Probe.preview.html`: Б1, Б12, Б34 — PASS, `ВЕРДИКТ: OK` (2 замечания на
содержимом-образце шаблона); `kit-build --check`, `assemble --check` — OK; гейт по изменениям —
`ВЕРДИКТ: OK (19 шаг.)`; повторный вызов — ЗГ3 по шести файлам, файлы не тронуты. В рабочем
дереве: гейт `ВЕРДИКТ: OK (15 шаг.)`, `vendor-scan` — OK.
*Найдено при проверке:* шапка-комментарий `Component.html` ДС называет теги `<script>` и `<div>`,
а проверка страниц витрины (`docs-split`) читает их как код — страница витрины виджета, где
комментарий оставлен, падает (ДС1, ДС19). Поэтому заготовка его не переносит. ДС не правилась.
Новые md в `apps/` требуют пересборки карты документации — `docs-index.mjs` в подсказке «затем».

## Э5. Короче handoff

Шаблон `/handoff` требует «до 80 строк, переписать целиком», но handoff RE0017 на рабочем
устройстве — 156 строк, 15 тыс. символов: разделы «Что сделано (Э3)», «(Э4)», «Проверки (Э3)»
копились по этапам. Его читает каждая следующая сессия `/resume`.

**Правка:** `.agents/commands/handoff.md` — «Что сделано» строкой на файл без пересказа;
«Проверки» — только последние `ВЕРДИКТ:`; разделов по этапам нет, файл переписывается
состоянием. Путь: в `handoff.md` и `resume.md` записан устаревший `apps/<Задача>/`, на практике
handoff лежат в `docs/tasks/RE…handoff.md` и в корне модуля (`apps/postrade/deals-app/`) —
записать оба места, `/resume` ищет в обоих, существующие файлы не переносить. Без новой
проверки.

**Эффект:** ~15 → ≤5 тыс. символов: −~4 тыс. токенов вывода на handoff и входа на `/resume`.

**Сделано (14.10.2026):** `commands/handoff.md` — два места хранения (рядом с файлом задачи
`docs/tasks/<ID>-<slug>.handoff.md`; иначе корень модуля или концепта), «файл — снимок, не
журнал», предел «до 80 строк и ~5 тыс. символов», «Что сделано» — строка на файл или папку без
пересказа, «Проверки» — только последние `ВЕРДИКТ:`, разделов по этапам нет.
`commands/resume.md` п. 1 — поиск в обоих местах, список при отсутствии — из обоих.
Устаревший путь `apps/<Задача>/` заменён и в указателях: `process.md` (ссылка на команду
вместо пути), `.agents/README.md` (схема и §10), `ai-designer.md` («handoff пишешь сам»).
Существующие handoff не переносились. Новой проверки нет.

**Уточнено в RE0021 (14.10.2026, решение человека):** новые handoff — только в `docs/tasks/`
рядом с задачей; работа без файла задачи сначала заводит короткую задачу по шаблону. Корень
приложения остался только для старых handoff — `/resume` ищет их там.

## Э6. Инструктаж — вынести, не удалять

Поэтапно, файл за заход, каждый шаг — отдельный дифф человеку.

**Что лишнее (символов):** `process.md` 37 тыс. (читают все роли каждую сессию; §5 «каркас»
8,7 тыс. повторяет `design-system/AGENTS.md` §5 и `screen-assembly`); `screen-builder.md`
32 тыс. (история «уроки 29.08.2026» 3,3 тыс., разбор ошибок конструктора документации);
`ai-designer.md` 28 тыс. (сценарий страниц документации); разделы docs-split в `screen-review` и
`composition-review` ~8 тыс.

**Шаги:**

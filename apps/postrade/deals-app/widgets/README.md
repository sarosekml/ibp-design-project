# widgets — виджеты модуля deals-app

Модули, из которых собираются страницы: тайлы, их модальные окна и прочие составные части
экрана. Папка разложена по группам (форма приложения, `apps/README.md`): сейчас здесь
`tiles/` и `modals/`. Имена сверены с деревом фронтенда 24.09.2026 (таблица — README
модуля). История папки: `post_local_components/` → `components/` → `widgets/`. Компоненты
дизайн-системы сюда не копируются — здесь живёт только то, чего в `design-system/` нет и
что принадлежит направлению.

## Зачем

Страница не собирается каждый раз с нуля и не держит в одном HTML-файле всё про все свои
объекты. Страница знает **перечень модулей**, которые в неё входят; сам модуль правится
точечно в собственных файлах, а страница подхватывает изменения. Если правка на странице
касается конкретного модуля — правится модуль, а не страница.

## Устройство

- Папка на модуль внутри своей группы: `widgets/<группа>/<Модуль>/` — `tiles/KNRTile/`,
  `modals/KNRModal/`. Виджет общий для раздела `postrade`: его вшивают и страницы
  соседних модулей (README модуля, «Виджеты»).
- **Тайл и его модальное окно лежат в разных группах**: тайл — в `tiles/`, окно — в
  `modals/`, как у фронтенда (`DealTeamTile` ↔ `DealTeamModal`). Связь записана в паспортах:
  `opens` у тайла, `opensFrom` у окна.
- **Подчасть окна живёт в его папке**, отдельной подпапкой, если у неё свои файлы —
  так фронтенд держит `CounterpartyCards` и `FICards` внутри своих модалок. Здесь так
  лежит `modals/KNRModal/CounterpartyCard/`. Вложенное окно подтверждения — просто
  файлом в папке окна (`modals/KNRModal/KNRConfirmModal.html`), паспорт у него общий с
  окном.
- Правила заполнения — страница ДС «Локальные компоненты»
  (`design-system/pages/patterns/LocalComponents.html`), заготовка — `design-system/templates/local-component/`.
  **Эта страница читается целиком** — перед тем, как заводить модуль или планировать
  правку: исключение из запрета читать страницы ДС целиком названо в
  `design-system/AGENTS.md` §4.

| Файл | Когда появляется |
|---|---|
| `<Модуль>.html` | сразу: фрагмент разметки с одним корневым элементом, без `<html>`/`<link>`/`<script>` |
| `<Модуль>.md` | сразу: паспорт; неизвестное пишется как `не решено (ДД.ММ.ГГГГ)`, не догадкой |
| `<Модуль>.css` | когда у модуля появляется внутренняя раскладка |
| `<Модуль>.js` | только если модулю нужно поведение, которого нет в рантаймах ДС. Сборщик `.js` не подключает — тег ставит страница сама, после `ds-body.js` |
| `fixtures.json`, `baseline.png`, `CHANGELOG.md` | когда модуль наполняется содержимым |
| `<Модуль>.doc.html` | страница документации модуля — пока не перенесена (ниже, «Документация модулей») |

## Механика подключения — ассемблер

Выбрана 19.09.2026. Страница ставит на место модуля метку, а место в сетке задаёт классом
на самой метке:

```html
<ds-include src="../widgets/tiles/KNRTile/KNRTile.html" class="col-3 colw-6"></ds-include>
```

Собирает страницу общий сборщик `.agents/tools/assemble.mjs` (с 24.09.2026; до того — `tools/` приложения):

```bash
node .agents/tools/assemble.mjs          # все источники apps/
node .agents/tools/assemble.mjs <файл>   # один
```

Источник `<имя>.html` превращается в самодостаточный `<имя>.preview.html` — **открывают
двойным кликом именно его**. После правки любого модуля или источника — пересобрать.

**Почему сборка, а не рантайм.** В ДС есть `scripts/ds-include.js`, который делает то же
самое в браузере, но он тянет фрагмент через `fetch`, а `fetch` по `file://` не работает.
Страницы здесь открываются двойным кликом, поэтому вшивание делается до открытия.
Контракт у ассемблера тот же, что у рантайма: `id` и `class` с метки переносятся на корень
фрагмента (прежнее значение заменяется, а не дублируется вторым атрибутом),
`state`/`mode` становятся `data-state`/`data-mode`, а CSS модуля — файл рядом с `src` —
подключается линком в `<head>` (атрибут `css="…"` переопределяет путь, `css="none"`
отключает).

**Модальные окна — метками в конце `body` страницы**, а не внутри тайла: скрим, вложенный
в скрытого родителя, не показать. У фрагмента один корневой элемент, поэтому каждый скрим
(окно, окно подтверждения) — свой файл и своя метка. Метки внутри фрагмента сборщик не
раскрывает, поэтому подчасть окна (шаблон карточки контрагента) страница тоже вшивает
своей меткой рядом с окном.

Инструменты приёмки фрагмент экраном не считают: `layout-check` и `ds-lint-cli` печатают
на нём `ПРОПУЩЕН:` и проверяют собранный файл. Определение фрагмента — в
`.agents/tools/fragments.mjs`.

## Связи между модулями

Модули не изолированы, и это часть замысла:

- Сущность из тайла дерева продуктов переносится в соседний тайл и отображается там; в
  дереве она остаётся, но меняет вид — видно, что она вложена в другой тайл.
- Признак в одном тайле (например, отмеченный чекбокс) управляет тем, показывается ли
  другой тайл — на этой же или на другой странице. Значит, признак принадлежит сделке, а
  не странице: система должна знать, что у конкретной сделки есть флаг, влияющий на
  конфигурацию другого экрана.

Модель хранения таких признаков в целом **не определена**. Определён первый случай —
состав участников сделки и её КНР (21.09.2026): его держит `CounterpartiesStore`
(`../data/counterparties-store.js`), сохраняет адаптер `PostApi` (`../data/post-api.js`),
контракт — `../data/API.md`. Окно КНР правит состав, тайл «КНР» и колонка «КНР» реестра
его читают. Следующие признаки сделки — по тому же образцу: стор направления + адаптер,
модули друг друга не знают.

Второй случай — **деск** (23.09.2026): он лежит в команде сделки, а управляет тем,
показывается ли тайл «Сведения о проекте» (ряд есть у деска «Недвижимость»). Признак
живёт в записи сделки (`DealsStore`), правит его окно «Команды сделки», а показ ряда
решает страница (`Deal.html`, `applyProjectInfo`). Зависимость односторонняя и записана у
зависимого — `ProjectInformationTile` объявляет `dependsOn: [DealTeamTile]`; обратной связи
нет. Ни один из двух тайлов про другой не знает — иначе получился бы цикл, который правила
запрещают.

## Режим правки

Режим прав приходит на модуль атрибутом `data-mode` и бывает двух видов: `edit` — действия
правки видны, `view` — они не рисуются вовсе (а не выключаются). Вид каждого режима держит
собственный CSS модуля, по образцу шаблона ДС (`templates/local-component/Component.css`).
Режим выставляет страница, модуль его не вычисляет.

Статус сделки сильнее роли. В статусах «Активная», «Погашена», «Ожидает подтверждения» и
«Подтверждение изменений» правка сущностей сделки невозможна, и страница ставит `view` всем
модулям при любой роли — правило живёт в `DealsStore.isEditable` (`../data/deals-store.js`).
Основание — «Текущий портфель.md» (`../refs/`, «В активной сделке нельзя редактировать
сущности») и решение человека 21.09.2026.

Выключенного действия с подсказкой-причиной нет: запрет по статусу — это тот же «Только
просмотр». Так же говорят правила ДС для локальных компонентов с версии 1.005.

## Документация модулей

В прототипе у наполненных модулей и их окон были страницы документации (`<Модуль>.doc.html`
по каркасу `ds-split`) и витрина локальных компонентов направления. Сюда они пока **не
перенесены** (решение человека 24.09.2026): инструменты приёмки этого репозитория считают
такую страницу экраном, а метки внутри фрагментов сборщик не раскрывает. Переезжают вместе
с оснасткой, которая это умеет; до того описание модуля — его паспорт `<Модуль>.md`.

## Состав

13 тайлов страницы сделки (`../pages/Deal.html`), три их модальных окна и одна подчасть окна.
Наполнены три тайла: `KNRTile` (20.09.2026), `DealPeriodTile` (22.09.2026), `DealTeamTile`
(23.09.2026) — у каждого своё окно. Остальные 10 тайлов — заглушки (`data-state="empty"`):
оболочка есть, состав полей не согласован.

**Заглушка не растягивает ряд** (решение человека 22.09.2026). Тело заглушки — одна строка
«Данные ещё не заведены» по центру (`.lc-<модуль>__stub`, Body M, `--text-inactive`), без
EmptyState: его иллюстрация и отступы дают ≈324px, а тайлы страницы по умолчанию стоят в
минимальной высоте 200px, и выше ряд становится только по содержимому наполненного тайла.
Центрирование держит CSS модуля (`.tile__body` растянут на свободную высоту тайла). Новая
заглушка заводится так же.

`KNRTile` — образец предметного модуля: фрагмент держит все состояния сразу, а показывает
нужное собственный CSS по `data-state` / `data-mode`. `CounterpartyCard` — образец
переиспользуемой подчасти: фрагмент отдаёт `<template>`, а карточки по нему рисует
потребитель из своего стора.

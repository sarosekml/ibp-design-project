# API данных направления Post

Контракт между страницами направления и хранилищем данных. В этом репозитории
сервера, который его исполняет, пока нет (раздел «Локальный сервер»): адаптер
`post-api.js` работает в режиме `local` и пишет в localStorage браузера. Настоящий
бэкенд реализует тот же контракт, и тогда меняется только адаптер — страницы и
сторы остаются как есть.

## Кто с кем говорит

```
страница ─▶ CounterpartiesStore (counterparties-store.js) ─┐
страница ─▶ ProductTreeStore (product-tree-store.js) ──────┴▶ PostApi (post-api.js) ─▶ API
```

- Страницы и компоненты зовут только стор.
- Стор зовёт только `PostApi`.
- `PostApi` выбирает режим один раз, при загрузке страницы, — общий для всех ресурсов:

| Режим | Когда | Куда пишется |
|---|---|---|
| `server` | страница открыта по http(s), и `GET /api/post/participants` ответил 2xx | база сервера |
| `local` | страница открыта двойным кликом (`file://`) или с сервера без этого API | `localStorage` браузера, ключи `ibp.post.participants` и `ibp.post.product-trees` |

В режиме `local` правки видны только в этом браузере. Консоль сообщает об этом один раз.

## Состав участников сделки

Запись о сделке хранит только ссылки на базу контрагентов (`mock-counterparties.js`):

```json
{ "members": ["ul-11", "ul-2"], "knr": ["ul-2"], "updated": "2026-09-21T09:30:18.175Z" }
```

| Поле | Что это |
|---|---|
| `members` | id контрагентов — участников сделки, в порядке добавления |
| `knr` | те из участников, кто отмечен ключевым носителем риска; подмножество `members` |
| `updated` | время сохранения, ISO 8601; ставит сервер |

Если сделку не сохраняли, записи о ней нет. Тогда стор собирает начальный состав из поля
`knr` сделки в реестре (`mock-deals.js`). Имена КНР для таблицы портфеля стор тоже
вычисляет из базы контрагентов, поэтому хранятся только id.

## Дерево продуктов сделки

Запись о сделке хранит дерево целиком — продукты ДИД, продукты, инструменты и транши
(typedef `DealProductTreeRsDto`, `mock-deal-trees.js`), коды узлов — из каталога
`mock-product-catalog.js`, связи с ФИ — id карточек `mock-fin-instruments.js`:

```json
{ "tree": { "id": 1027, "productsDid": [ … ] }, "updated": "2026-09-30T12:00:00.000Z" }
```

| Поле | Что это |
|---|---|
| `tree` | дерево сделки; сохранённое перекрывает демо-дерево из `mock-deal-trees.js` |
| `updated` | время сохранения, ISO 8601; ставит сервер |

Если сделку не сохраняли, записи нет — стор показывает дерево из `mock-deal-trees.js`.
Плоские поля реестра (`mainProductDid`, `productsDidNames`, `productsNames`, `balances`,
`currencies`, `isPE`) стор вычисляет из дерева (`ProductTreeStore.summary`), поэтому
отдельно не хранятся. Правки в прототипе — ответ человека 30.09.2026 (задача
`docs/tasks/RE0001-product-row-tree.md`, вопрос 15): в продукте дерево сохраняется.

## Команда сделки

Через этот контракт **не ходит**. Команда — не ссылки на другую базу, а поля самой
сделки, поэтому она живёт в записи реестра (`mock-deals.js`) и правится через
`DealsStore`, как остальные поля сделки:

```js
var team = DealsStore.byId(id);                 // чтение: поля прямо в записи
DealsStore.update(id, { desk: 'Недвижимость',   // запись: обычный патч
                        clientManager: 'Смирнов А.А.' });
```

| Поле записи | Что это |
|---|---|
| `desk` | направление, по которому ведётся сделка; значение из `DEALS_ENUMS.desk`. Обязательное |
| `director` · `regionalDirector` · `manager` · `tsupEmployee` · `clientManager` · `creditInspector` · `riskEmployee` · `monitoringEmployee` · `pmzEmployee` · `prpaEmployee` · `legalEmployee` · `constructionExpert` | роли; значение — ФИО одного сотрудника из справочника `mock-team.js`. Отсутствует или пусто — роль не назначена |
| `<роль>Tab` — `directorTab`, `managerTab` и так далее | табельный номер назначенного сотрудника, строка из цифр. Пара есть у каждой роли, у деска её нет |
| `otherParticipants` | свободная строка: люди не из банка, несколько через запятую |
| `restricted` | «Да» / «Нет» — сделка ограниченного доступа |

Четыре поля (`desk`, `director`, `manager`, `tsupEmployee`) и `restricted` были в записи
и раньше — их показывает реестр портфеля. Остальные добавлены 23.09.2026 вместе с тайлом
«Команда сделки».

**Почему имя и номер порознь.** Поле роли хранит только ФИО — его читают реестр портфеля
и тайл, и номеров там не показывают. Номер нужен там, где сотрудника выбирают: в окне
правки он виден за именем («Андреев М.А. 100101») и различает однофамильцев. Склеивает
для показа и разбирает обратно `DealTeamModal.js` (`personValue` / `splitPerson`):
хвостовая группа цифр — номер. Если имя ввели руками, не выбрав из списка, номер остаётся
пустым, а не подставляется по совпадению ФИО.

Справочник сотрудников (`mock-team.js`, `MOCK_TEAM_ROSTER`) — только для списков окна:
это кандидаты, а не данные сделки. Туда же положена демо-карта
`MOCK_DESK_REQUIRED` — какие роли обязательны при каком деске; настоящая карта у
владельца продукта.

**Хранение — в памяти вкладки**, как у всего `DealsStore`: правка видна до перезагрузки
страницы. Понадобится переживать перезагрузку — команда пойдёт тем же путём, что состав
участников: стор направления плюс адаптер `PostApi`, эндпоинт по образцу ниже.

## Описание сделки

Тоже **не ходит** через этот контракт: поля самой сделки, правятся через `DealsStore`
окном тайла «Описание сделки» (`DealDescriptionModal`). Хранение — в памяти вкладки.

| Поле записи | Что это |
|---|---|
| `description` | суть сделки, свободный текст |
| `operationsComment` | комментарий Operations |
| `additionalIncome` | дополнительные доходы, свободный текст; тайл не показывает, только окно |
| `ceParticipation` · `ifDeskParticipation` · `restructured` | участие ЦЭ, участие Деска ИФ, реструктуризация — `true` / `false` |
| `riskCategory` | категория риска ЦУП: `A` · `B` · `C` · `D` · `UNDEFINED` («не определена»); `null` — не присвоена. Подписи и пояснения — `DEALS_ENUMS.riskCategoryNames` / `.riskCategoryHints` |
| `relatedDeals` | связанные сделки: `[{ name, opportunityId }]`; приходят из системы, окно их не правит |
| `gsz` | группа связанных заемщиков; значение из `DEALS_ENUMS.gsz`. Поле реестра |
| `jointness` | совместность — краткое имя территориального банка из `DEALS_ENUMS.jointness` (полные — `.jointnessNames`); пустая строка — совместности нет. Поле реестра |
| `finTpl` | «Да» / «Нет» — фин. расчёты ведутся в шаблоне Excel. Поле реестра |

Три последних поля были в записи и раньше — их показывает реестр портфеля, поэтому формат
у них прежний (строки). Остальные добавлены 24.09.2026 и названы в стиле API
(typedef `DealDescriptionFields`, `data/mock-deals.js`). Отсутствующее поле читается как
пустое. `jointness` до 24.09.2026 хранил «Совместная» / «Не совместная»; значение
уточнено по макету тайла.

Окно «Документы ЭКД» данных сделки не правит: список участников берёт из
`CounterpartiesStore.members()` — раздел «Состав участников сделки» выше.

## Эндпоинты

| Метод и путь | Ответ |
|---|---|
| `GET /api/post/participants` | `200` — `{ "<номер сделки>": запись, … }`; только сохранённые сделки |
| `GET /api/post/participants/:dealId` | `200` — запись; `404` — сделку не сохраняли |
| `PUT /api/post/participants/:dealId` | тело `{ members, knr }` → `200` `{ ok: true, updated }` |
| `DELETE /api/post/participants` | `204` — база очищена (для показов) |
| `GET /api/post/product-trees` | `200` — `{ "<номер сделки>": { tree, updated }, … }`; только сохранённые сделки |
| `GET /api/post/product-trees/:dealId` | `200` — запись; `404` — дерево сделки не сохраняли |
| `PUT /api/post/product-trees/:dealId` | тело `{ tree }` → `200` `{ ok: true, updated }` |
| `DELETE /api/post/product-trees` | `204` — база деревьев очищена (для показов) |

**Проверки при записи** (`400` с `{ error }`):

- номер сделки и id контрагентов — `[A-Za-z0-9_-]`, от 1 до 32 символов;
- `members` и `knr` — массивы без повторов, не больше 500 записей;
- каждый id из `knr` есть в `members`;
- `tree.id` совпадает с номером сделки из пути; у узла `fiIds` — не больше двух.

Тело больше 64 КБ — `413`. Другие методы — `405`.

## Поиск контрагентов (для настоящего бэкенда)

В прототипе этого эндпоинта **нет**: база контрагентов — мок-файл `mock-counterparties.js`
на фронте, поиск выполняет `CounterpartiesStore.search`, и работает он одинаково с сервером
и без него. Ниже — контракт, по которому поиск пойдёт на настоящий бэкенд. Тогда адаптер
получает метод `PostApi.search`, а стор зовёт его вместо поиска по мок-базе.

| Метод и путь | Ответ |
|---|---|
| `GET /api/post/counterparties?kind=ul&name=&inn=&kpp=&ogrn=&kio=&dealId=` | `200` — массив юрлиц |
| `GET /api/post/counterparties?kind=fl&parentId=&inn=&birthDate=&passport=&phone=&dealId=` | `200` — массив физлиц |

Запись ответа — в форме базы: `id`, `kind`, `name`, `subheader`, `parentId` (у физлица),
`fields`, `gsz`, `risk`, `contacts`.

Правила — те же, что у стора сейчас:

- заполненные параметры соединяются по «И»; ни одного — `400`, поиск не выполняется;
- `name` — подстрокой, без учёта регистра, кавычек и разницы ё/е; коды (ИНН, КПП, ОГРН, КИО,
  паспорт, телефон) — подстрокой по цифрам; `birthDate` — точно, `ДД.ММ.ГГГГ`;
- участники сделки `dealId` в результат не попадают;
- физлица ищутся только среди физлиц юрлиц — участников сделки `dealId`; `parentId` сужает
  поиск до одного из них.

## Локальный сервер

Не перенесён (решение человека 24.09.2026): своей папки `tools/` у модуля нет, место
для сервера данных в репозитории ещё не выбрано. Пока его нет, `PostApi` сам
переходит в режим `local` — участники и КНР сохраняются в localStorage браузера,
страницы открываются двойным кликом.

Каким он был в прототипе: Node без зависимостей, слушает только `127.0.0.1`, раздаёт
статику от корня репозитория и исполняет `/api/post/participants` по контракту выше;
база — один JSON-файл вне git, запись атомарная, запросы на запись — по очереди.
